# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev       # start Vite dev server (http://localhost:5173)
npm run build     # production build to dist/
npm run preview   # serve the production build locally
```

Pure business logic in `utils.js` is covered by a Vitest suite (`npx vitest run`, 100+ tests in `src/utils.test.js`) — run it after touching utils.js. There is no linter or type checker, and components are untested.

## What this is

FactoryOS is a single-page factory floor management dashboard: machine status/production tracking, casting-type routing, stock/WIP, attendance, wages, and alerts. It was migrated from a single-file HTML prototype into this Vite + React project — that original file has since been removed from the repo (it predates Firebase Auth, so it no longer works against the current Firestore rules anyway). The migration was a straight structural port: components, business logic, and CSS class names were kept verbatim, just split into files.

## Data layer: Firestore via a small wrapper

All persistence goes through `src/firebase.js`, which exports a single `fb` object. Two data schemes live side by side:

**Legacy flat-doc scheme** — everything except users. One Firestore document per key, all inside a single collection literally named `factoryos`:
```js
fb.get(key)          // read a document's `value` field
fb.set(key, value)   // write a document's `value` field
fb.sub(key, cb)      // onSnapshot subscription, cb receives the value
```
Known keys: `machines`, `alerts`, `casting_types`, `wip`, `stock_log`, `attendance`, `overtime`, `sessions`, `wage_log`, `adjustments`, `orders`, `maintenance_schedules`, `maintenance_log`, `inspection_log`, `assembly_models`, `purchased_components`, `salary_sheets`. **Do not rename these keys** — this app reads/writes the same live Firestore project (`pew-production-dev`) that the original HTML prototype used. The old `factoryos/users` doc still exists but is deprecated/read-only — see Authentication below.

**User profiles** — a real collection, `factoryos_users/{uid}`, one doc per user: `fb.getUserProfile(uid)`, `fb.listUserProfiles()` (staff-only), `fb.findUserProfileByUsername(username)` (staff-only), `fb.createUserWithProfile(username, password, profile)`, `fb.setUserProfile(uid, profile)`, `fb.deleteUserProfile(uid)` (all admin-only except the self-scoped `getUserProfile`).

Firebase config comes from `import.meta.env.VITE_FIREBASE_*` (see `.env` / `.env.example`), not hardcoded.

Almost all Firestore reads/writes for operational data happen inside `Dashboard.jsx` — it loads the flat-doc keys on mount, subscribes to live updates via `fb.sub`, and debounces writes of `machines` (600ms after any change). Modals that mutate shared state (e.g. `CastingTypesModal`, `StockView`, `AttendanceModal`) call `fb.set` directly rather than routing through Dashboard. User-profile-consuming modals (`UserModal`, `AssignModal`, `AttendanceModal`, `WageRegisterView`) each self-fetch via `fb.listUserProfiles()` in their own `useEffect` on mount — `Dashboard.jsx` deliberately does **not** hold a central `users` list, since `listUserProfiles()` is staff-only and Dashboard is rendered for every role including plain operators.

## Authentication

Firebase Authentication (Email/Password) gates all Firestore access — see `firestore.rules` in the repo root. Usernames aren't emails, so sign-in uses a synthetic address under the hood (`${username}@factoryos.local`, see `toEmail` in `firebase.js`); the UI still shows a plain username field. Persistence is **per-login**: the default is `browserSessionPersistence` (cleared on browser close) — deliberate, since shop-floor terminals get handed off between operators across shifts and must not carry a stale login — but the login screen's "Keep me signed in on this device" checkbox switches that sign-in to `browserLocalPersistence` for operators' personal phones (`fb.signIn(username, password, remember)`; the checkbox preference itself is remembered per device in `localStorage['fos_remember']`).

`App.jsx` drives the auth flow via `fb.onAuthChange`, fetching the signed-in user's own `factoryos_users` profile doc before rendering `Dashboard`. If a Firebase Auth session is valid but the profile doc is missing (an admin removed the user), `App.jsx` signs them out immediately with an explanatory message — that's the intended way "remove user" revokes access, see the caveat below.

Creating a new user (`UserModal` → `fb.createUserWithProfile`) spins up a throwaway secondary Firebase App instance so the client SDK's `createUserWithEmailAndPassword` doesn't sign the admin out of their own session — see the comment in `firebase.js`.

Removing a user (`UserModal` → `fb.deleteUserProfile`) calls the `deleteUserAccount` Cloud Function (`functions/index.js`) rather than deleting the Firestore doc directly — this fully deletes both the Firebase Auth credential and the profile doc in one step, so a removed user's username/password stops working immediately. The function itself re-checks that the caller is an admin (reads the caller's own profile doc server-side) — never trust the client-side `isAdmin` UI gate alone for this.

**Password reset**: the `resetUserPassword` Cloud Function (same admin-gate pattern as `deleteUserAccount` — both share `requireAdmin` in `functions/index.js`) sets a new password on an existing account, since synthetic emails mean Firebase's native reset-email flow has nowhere to deliver. In the UI it's the optional "New password" field in UserModal's edit form — blank keeps the current password.

**Employee register / lifecycle**: `UserModal` doubles as an employee register — profiles carry `dateOfJoining`, `aadhaar` (optional, 12-digit-validated), and `dateOfLeaving` (all optional, all roles). Leaving is a **soft-deactivate**, distinct from the hard `deleteUserAccount` Remove: setting `dateOfLeaving` keeps the record but two pure helpers in `utils.js` drive the consequences — `isActiveEmployee(user, today)` (`!dateOfLeaving || dateOfLeaving > today`; future-dated leaving stays active until then) gates login (`App.jsx` signs a left employee out with a "no longer active" message via the existing `revokedMsg` flow) and active rosters (`AttendanceModal`/`AssignModal` operator lists), while `employedDuring(user, from, to)` (missing dates ⇒ always included) keeps a departed operator in the wage register (`registerOperators`) and salary sheet (`buildSalarySheetCsv` filters its roster per month) for periods they actually worked. Reactivation = clear `dateOfLeaving`. The Firebase Auth credential is untouched (the app-level gate refuses entry). **Aadhaar sensitivity caveat**: it lives in the `factoryos_users/{uid}` profile doc, which `firestore.rules` lets any staff (admin+supervisor) read via `listUserProfiles` (needed for assign/attendance) — so a supervisor could read it through the raw API even though only the admin-only Manage users UI displays it. Acceptable for a small trusted team; a separate admin-only `factoryos_hr/{uid}` collection is the path if stricter isolation is ever wanted.

**Backups**: the `dailyBackup` scheduled function (03:30 IST nightly) snapshots every `factoryos` flat doc plus all `factoryos_users` profiles into the `factoryos_backups` collection (doc id `${date}~${key}`, so each stays under the 1MB doc limit; users under `${date}~__users`). Retention: 14 dailies + every 1st-of-the-month snapshot kept forever. Clients can't read or write the collection (firestore.rules default-deny; the function's Admin SDK bypasses rules). Restore = copy a backup doc's `value` field back over `factoryos/{key}` in the Firebase console. This protects against app-level mistakes (bad writes, accidental resets) — it is not a cross-project disaster-recovery story.

`firestore.rules` and `functions/` are version-controlled here but not auto-deployed — run `firebase deploy --only firestore:rules,functions` (or deploy each separately) once you have the Firebase CLI installed and are logged in. See `firestore.rules`' own header comment for the required rollout order (app must ship and be verified *before* the rules are tightened, never the other way around, or you lock every client out). Cloud Functions require the Blaze (pay-as-you-go) plan.

## Component architecture

```
src/
  constants.js   — seed/config data: MACHINES_SEED, SHIFT_CFG, BADGE, DEFAULT_USERS, etc.
  utils.js       — pure helpers: shift-slot logic, WIP/routing resolution, OT pay calc
  firebase.js    — the fb wrapper described above
  App.jsx        — auth gate: tracks Firebase Auth state, renders LoginScreen or Dashboard
  components/ErrorBoundary.jsx — class component wrapping <App/> in main.jsx
  components/
    *.jsx              — one file per modal/banner (Modal, LoginScreen, UserModal,
                          CastingTypesModal, AssignModal, etc.), plus PageView.jsx (the
                          full-page view shell) and the three page views built on it:
                          StockView, OrdersView, WageRegisterView
    dashboard/
      Dashboard.jsx    — owns ALL state (~25 useState), effects, and handlers; the
                         single source of truth for machines/alerts/castingTypes/wip/etc.
      Topbar.jsx, ShiftBanner.jsx, StatsRow.jsx, MachineGrid.jsx, OutputChart.jsx,
      ShiftOverview.jsx, MachineDetailPanel.jsx, AlertsPanel.jsx, AlertItem.jsx,
      OperatorHome.jsx, ProductionActions.jsx, AttentionStrip.jsx
                       — presentational subcomponents; they receive state and setters
                         as props from Dashboard and contain no Firestore calls of
                         their own (except via callbacks passed down).
```

`Dashboard.jsx` is the one file where nearly everything converges — any change to machine/shift/casting-type state, or to which modal is open, touches this file. When adding a new modal or dashboard panel, follow the existing pattern: state and `fb.set` calls live in `Dashboard.jsx`, the panel itself is a prop-driven component with no direct Firestore access.

**Global UX helpers** (both use the same imperative register pattern — a module-level `showFn` set by a host component that App mounts once): `confirmDialog(msg)` (`src/confirmDialog.js` + `ConfirmDialog.jsx`, promise-based confirm) and `toast(msg)` (`src/toast.js` + `ToastHost.jsx`, fire-and-forget ~2.6s save confirmations, stacked max 3, bottom-center). Toasts are for actions whose modal closes silently (shift complete, log progress, breakdown, repair, decisions, inspections — success paths only; the assembly BOM hard-block deliberately does NOT toast since its modal stays open showing shortages). Modals with their own inline "saved" messages don't also toast. App.jsx also renders a fixed-bottom `.offline-banner` driven by `navigator.onLine` + window online/offline events, with a "Back online" toast on reconnect — Firestore queues writes in memory while offline and syncs on reconnect as long as the tab stays open.

## Navigation — views and the grouped topbar

Dashboard's `view` state is six-valued: `'floor'` (default for staff — the machine grid main layout), `'analytics'` (admin+supervisor), `'myshift'` (operator home, the **default for `role==='operator'`** and only reachable by operators via My shift / Floor tabs in the shift-tabs row), plus three full-page staff views — `'stock'` (StockView), `'orders'` (OrdersView, both admin+supervisor) and `'wages'` (WageRegisterView, **`role==='admin'` only** — supervisors must never see pay data). Each swaps the `.main-layout` block while Topbar/ShiftBanner stay (the AnalyticsView pattern); the three new ones wrap their content in the shared `PageView` shell (`src/components/PageView.jsx`: `.page-body` 960px-capped body + "← Back to floor" header, scrolls to top on mount). A defensive `safeView` normalization in Dashboard's render falls back to `'floor'` for any view the current role isn't entitled to. The shift selector tabs and ShiftBanner are hidden while on `'myshift'` — the operator home spans all shifts, so a viewShift selector there would mislead. These three views were modals until mid-2026; quick transactional actions (Assign, LogProgress, ShiftComplete, Breakdown, decisions) and medium screens (Maintenance, Inspections, master-data CRUD) deliberately stay modals.

**AttentionStrip** (floor view, `isAdmin` only, first child of `.content-area`): one clickable chip row consolidating everything needing a decision — overdue/due-soon orders → `'orders'` view, maintenance due → MaintenanceModal, low stock (casting types AND purchased components) → `'stock'` view, pending shortfall/setting reviews → smooth-scrolls to the alerts panel (`id="floor-alerts"`). Fed by `attentionSummary(...)` in `utils.js` (pure, tested), which is also the source for the Topbar Materials/Quality ⚠ badges — one computation, so strip and badges can never disagree. Renders nothing when all clear. It replaced the old admin low-stock banner (which only covered casting types). Chip severity: danger when anything is overdue (low stock is always danger), warn otherwise.

**OperatorHome** (`'myshift'`) renders one card per assignment slot via `operatorAssignments(machines, username)` in `utils.js` — a cnc machine assigned to the same operator on day AND night yields two cards, each carrying its own `shiftKey` (never `viewShift`). Cards embed **ProductionActions** (extracted from MachineDetailPanel, shared by both — the `{machine, pj, shiftKey, mode}` payloads it sends to `setLogProgressData`/`setShiftCompleteData`/`setLineInspectionData` are load-bearing for `handleShiftComplete` and wage logging; its `compact` prop hides the job/target lines the card header already shows). Breakdown-status cards show a danger notice and no actions (repair is admin-only, on the floor view). The alerts feed stays in the sidebar (read-only for operators).

**Topbar** groups staff actions into four data-driven dropdown sections — Materials (Stock, Orders ⚠, Purchased components), Quality (Inspections, Maintenance ⚠, Breakdown history), Insights (Analytics, Download report), Manage (Production jobs, Assembly models, + `role==='admin'` only: Machines, Users, Attendance, Wages) — plus standalone Floor, Assign jobs (most-used staff action, deliberately not buried in a menu), Online (all roles), and Sign out. Section buttons inherit their items' ⚠ badges (Materials←ordersAttention, Quality←maintAttention). Each `.tb-group` renders both a desktop dropdown trigger (`.tb-group-btn`) and a mobile group header (`.tb-group-hdr`); CSS picks the presentation per breakpoint (≤900px = flat grouped list inside the hamburger panel), no JS media query. When adding a staff feature, add an item to the right section's config array in Topbar.jsx — don't add a new top-level button.

## Domain model — shifts, casting types, routing

- **Machines** are either `cnc_vmc` (day/night shift slots, stored under `machine.shifts.day` / `machine.shifts.night`, each an independent assignment) or `manual` (single flat shift, fields directly on the machine object). Use `getSlot`/`withShift`/`patchMachineShift` from `utils.js` to read/write machine state — never access `machine.shifts.day` etc. directly, since manual machines don't have a `shifts` object at all.
- **Casting types** define a raw material plus one or more **routes**, each an ordered list of **steps**. A step is either `fixed` (one specific node/operation) or `floating` (a group of nodes that can run in any order relative to each other, sharing a WIP pool keyed by the group's gate). See `resolveStage`, `routeNodeIds`, and the WIP-key helpers (`wipKey`, `getWip`) in `utils.js`.
- **Side-tracks** (`route.sideTracks[]`) extend this for operations that can run any time relative to OTHER backbone steps too, not just relative to each other — e.g. "Drill Tap and Spot Face can happen any time after Bore-Face-OD, before or after Milling or Side Drill, but both must finish before Balance." Each entry is `{nodeIds, unlocksAfterStepIndex, joinsBeforeStepIndex}`. The join is computed from monotonic cumulative counters (`chainarrived`/`tracksarrived`/`joinreleased` WIP keys), never from `min()` of two live/depletable pools — see the large header comment on `computeShiftCompletionUpdate` in `utils.js` for why the naive version silently produces wrong numbers once the two sides finish on separate shifts. v1 only supports one side-track per join point.
- **WIP** (work-in-progress) tracks how many pieces are ready to enter each route step. It's a flat `{[wipKey]: count}` map. `normalizeCastingTypes` migrates older/looser Firestore data shapes (pre-routing `{stages:[...]}`, flat `{nodeIds:[...]}` routes, or routes saved before side-tracks existed) into the current `{steps:[...], sideTracks:[...]}` shape — call it on any casting-type data read from Firestore before trusting its shape.
- `handleShiftComplete` in `Dashboard.jsx` calls `computeShiftCompletionUpdate` (in `utils.js`), the most complex piece of business logic: it moves consumed/produced pieces through the WIP graph (raw stock → fixed/floating/side-track steps → finished units), logs stock movements, and calculates overtime pay via `calcOtPay`. Read it carefully before modifying — the floating-step WIP release logic (via a "gate" and per-node "done" counters) and the side-track join logic are not obvious from a quick skim.

## Wages — piece-rate vs daily vs monthly

**Access**: the Wages and Attendance topbar buttons are gated `role==='admin'` only (owner's decision — supervisors must not see pay data), unlike most staff screens which use the shared `isAdmin` (admin+supervisor) gate.

Each operator profile has a `wageType`: `'production'` (piece-rate), `'daily'` (missing = `'daily'`), or `'monthly'` (fixed salary, `monthlySalary` field). Pay rules live in two pure helpers in `utils.js` — `computeShiftPay` (one wage_log entry → pay: ≥target = full wage + `calcOtPay` overtime; <target gated by the shortfall review: approved = full, disapproved/pending = proportional) and `computeOperatorDayPay` (production users sum shift pays — multi-machine days can exceed one daily wage — falling back to attendance on no-shift days; daily and monthly users both get attendance × per-day-rate + OT, sharing the same branch).

**Monthly salary** is implemented as a substitution, not a new pay path: `computeOperatorDayPay` resolves the per-day rate as `monthlySalary / daysInMonth(date)` (real day-count of that date's calendar month, via the `daysInMonth` helper — not a flat ÷30) and then falls straight into the existing daily-wage attendance+OT logic. This one substitution is what makes absences prorate (a day only pays if present/half, same as daily), OT reuse the daily rule (`computeShiftPay` just wants a per-day number), and a date-range register prorate correctly (a full calendar month of present days sums to exactly the salary; a partial range sums proportionally; month-spanning ranges are correct because each day uses its own month's day-count). Every call site that resolves a per-day wage number (`WageRegisterView`'s per-day loop, `AnalyticsView`'s OT KPI) must branch on `wageType==='monthly'` the same way — don't just read `dailyWage`.

`handleShiftComplete` writes a **facts-only** entry (produced/target/ratePerHour/status, no money) to the `wage_log` flat doc (capped 2000, newest first); `handleDecisionSubmit` settles pending entries via the `alertId` join. `WageRegisterView` computes money at read time from these facts × the operator's *current* dailyWage/monthlySalary. Do not compute payroll from `alerts` — that doc is capped at 200 and drops older entries.

**Manual overtime**: production/piece-rate operators get OT automatically from completed shifts, but off-machine workers (daily/monthly) have no auto source. The `overtime` flat doc (`{[date]:{[username]:hours}}`, parallel to `attendance`) holds OT hours entered per person per day via a small "OT hrs" box on the AttendanceModal (all operators — the owner avoids double-counting machine workers himself). It reaches pay via `computeOperatorDayPay`'s optional `otHours` param (adds `otHours × wage/8` to OT in every branch, on top of any machine OT) and the salary sheet's "Hours Worked" column (`buildSalarySheetCsv` sums `productionOtHoursForMonth + manualOtHoursForMonth`). `otHours` defaults 0 so every other caller/test is unchanged.

Manual pay adjustments live in the `adjustments` flat doc (capped 3000): entries `{username, date, type:'food'|'conveyance'|'advance', amount, note, recordedBy}`, entered on the Wage register's "Allowances & advances" tab. Food/conveyance add to net payable, advances deduct; an over-advanced period shows a negative net (flagged red) that the admin settles/carries manually — there is deliberately no automatic balance carry-forward. `ratePerHour` is snapshotted per entry because setup-time-adjusted targets break the naive `(extra/target)×wage` ratio (see the regression test in `utils.test.js`).

**Monthly salary sheet** (WageRegisterView's third "Monthly sheet" tab): reproduces the owner's hand-built payroll Google Sheet. Each user profile carries a `payGroup` (`'cheque'|'cash'|'thekedar'|'office'`, set in UserModal; missing → "Ungrouped"); `buildSalarySheetCsv` in `utils.js` lays workers out in fixed group order with per-group Total rows and a grand TOTAL WAGES. **Crucially the CSV cells carry LIVE formulas** (`=IF(...)` for the owner's paid-Sunday rule, `=SUM(...)`, cell refs) — Google Sheets' importer (File → Import → Upload) evaluates quoted `=…` cells as real formulas, so the download is his own editable sheet pre-filled from app data (days worked via `workedDaysInMonth` = marked attendance present=1/half=0.5 PLUS any unmarked day with a completed shift counted as 1 — so basic wage never goes missing just because attendance was skipped while overtime auto-logged from a completed shift; daily/monthly wages, machine production OT hours via `productionOtHoursForMonth`, conveyance/advance/food from the adjustments ledger), not a dead export. Office group gets a base 1 paid holiday; the "public holidays this month" input adds a paid day for everyone (office = 1 + N). Column letters and formula shapes are in the `buildSalarySheetCsv` header comment — the row-ref correctness is the whole risk, so it's heavily tested. The `salary_sheets` flat doc (`{lastGeneratedMonth:'YYYY-MM'}`) records the last generated month; `salarySheetDue` + `attentionSummary.salarySheetDueMonth` drive an **admin-only** attention-strip chip that appears from the 5th of each month until that month's previous-month sheet is downloaded (the chip opens Wages on the Monthly-sheet tab via Dashboard's one-shot `wagesInitialTab`, cleared on leaving the view). The sheet uses the daily×days model for everyone including piece-rate operators — their app-computed pay stays on the Register tab for cross-checking. This is deliberately a **download**, not emailed: no external email service was added.

## Customer orders

The `orders` flat doc (capped 500) holds multi-line customer orders: `{id, customer, poRef, notes, createdDate, dueDate, createdBy, status:'open'|'completed'|'cancelled', items:[{castingTypeId, qty, dispatched}]}` — one line per casting type, no duplicates, no pricing (accounting is out of scope). Managed in `OrdersView` (admin+supervisor topbar button, which shows a ⚠N badge for open orders overdue/due within 3 days via `orderDueState` in `utils.js`). Dispatching from StockView's Stock out tab can optionally target an order line — `applyDispatchToOrder` (pure, tested) increments the line's `dispatched` (allowed to exceed qty) and auto-completes the order when every line is filled. Loose dispatches deliberately never touch orders; orders are cancelled, never deleted; there is no stock reservation per order (finished-on-hand shown for context only).

## Assembly / BOM production

Beyond casting types (raw material → machined route → finished stock), the factory also builds **assemblies**: a finished sellable product combining in-house machined parts (plate, cover — consumed from a casting type's own finished stock) with **purchased components** bought from vendors (lever kit, spring kit — no machining, no route). An assembly build is tracked like a shift — operator, target, LOG PROGRESS, MARK SHIFT COMPLETE — with identical rigor to a casting-route step, and it feeds wages through the exact same `wage_log`/`computeShiftPay` path (Phase 1 shipped no changes to any wage function — see below for why).

**Data shapes**: `purchased_components` (flat doc, array) — `{id, name, unit, vendor, lowThreshold, balance}`. Unlike castings' inferred-from-stock-in-history supplier, `vendor` is a direct field (single-sourced, Phase 1 scope). `balance` is a plain mutable number like `castingTypes[].rawBalance` — not a monotonic counter, so it can dip and self-heal on the next stock-in. `assembly_models` (flat doc, array) — `{id, name, unit, target, ratePerHour, shiftHours, bom:[{kind:'casting'|'purchased', itemId, qty}]}`. `target`/`ratePerHour`/`shiftHours` deliberately mirror a casting-type node's shape so `computeShiftPay`/`computeOperatorDayPay`/`calcOtPay` need zero changes — they only ever read `{produced,target,ratePerHour,status}` off a `wage_log` entry, agnostic to whether the job behind it was a casting step or an assembly build. Managed in `AssemblyModelsModal`/`PurchasedComponentsModal` (admin+supervisor topbar buttons — "Assembly models", "Purchased components").

**Machine assignment**: a `type:'assembly'` machine (seeded `ASM-1`/`ASM-2` in `MACHINES_SEED`) gets a `jobKind` toggle in `AssignModal` — "Casting route step" or "Assembly build" — since a casting route can legitimately end on an assembly-type machine too (e.g. a final-inspect node). Assembly assignment sets `machine.assemblyModelId` (and nulls `castingTypeId`/`routeId`/`nodeId`); the casting path is unchanged except it now also nulls `assemblyModelId`. `resolveJob(castingTypes, assemblyModels, machine)` in `utils.js` is the single place that disambiguates which kind of job a machine is running — `MachineGrid`, `AssignmentBanner`, and `MachineDetailPanel` all read through it instead of `resolveStage` directly.

**WIP namespacing**: `assemblyWipKey(modelId, key) = wipKey('asm:'+modelId, key)` in `utils.js` — prefixes every assembly-model WIP counter so an assembly-model ID can never collide with a casting-type ID sharing the same number, without relying on an ID-uniqueness assumption across the two entity types (see the collision test in `utils.test.js`). A new monotonic counter, `assembled` (written on the *casting type's own* key, `wipKey(ct.id,'assembled')`), tracks how much of a casting type's finished stock has been pulled into assembly builds — never decrements `finished` directly, same conservation-of-mass philosophy as `entered`/`finished`/`scrapped`. `finishedOnHand(wip, castingTypeId)` in `utils.js` is the canonical "how much of this casting type's finished stock is actually available" read (`finished − dispatched − assembled`, floored at 0) — `StockView` and `OrdersView` both call this shared helper rather than each keeping their own copy (they used to; that duplication is why this was consolidated).

**Consumption engine — `computeAssemblyShiftUpdate` in `utils.js`**: a deliberately *separate* pure function from `computeShiftCompletionUpdate`, not an extension of it — that function is a single-material flow through one route graph; an assembly build is "consume N differently-shaped inputs in fixed ratios, produce one output," a different problem shape entirely. Given `{model, machineName, consumed, total, newPieces, reworkPieces, defects}`, it checks every BOM line's `needed = consumed * line.qty` against `bomLineAvailable` (casting-kind → `finishedOnHand`; purchased-kind → `purchasedComponents[].balance`) **before committing anything**. This is a **hard, all-or-nothing block** — a deliberate departure from the rest of the app, which floors/warns rather than blocks (e.g. `StockView`'s Stock-out tab lets you over-deduct past `finishedOnHand` with a confirm dialog). The reason: `finishedOnHand` is a *derived read* off monotonic counters, not a live mutable balance like `rawBalance`. If `assembled` ever overshot `finished`, the `Math.max(0,...)` floor in `finishedOnHand` wouldn't just clip a display number — it would permanently and silently erase how far over you went, with no negative signal to notice or correct later (unlike `rawBalance`, which visibly goes negative and self-heals on the next stock-in). Blocking the whole build keeps that guarantee intact. On shortage, it returns `{ok:false, shortages:[{kind,itemId,itemName,needed,available}, ...]}` listing *every* short line at once, not just the first. `ShiftCompleteModal`'s `blockedShortages` prop renders these inline and the modal stays open — `Dashboard.jsx`'s `handleShiftComplete` returns early on `{ok:false}` without setting `shiftComplete:true` or writing a `wage_log` entry. On success: casting-kind lines increment `wipKey(ct.id,'assembled')` (nothing on `castingTypes` itself changes); purchased-kind lines decrement `purchasedComponents[].balance` directly; the model's own output increments `assemblyWipKey(model.id,'finished')` (defects increment `...,'scrapped'`); every consumption logs to `stock_log` with `stageLabel:'Consumed by assembly · ${model.name}'`, distinct from `'Finished goods dispatch'`.

**Analytics exclusion**: `isPipelineExit(stageLabel)` in `utils.js` (`stageLabel==='Finished goods dispatch' || stageLabel.startsWith('Consumed by assembly')`) replaces the old exact-match dispatch check in `aggregateDefects`/`aggregateFoundryScore`, so a casting type's finished stock being pulled into an assembly build doesn't inflate mid-route consumption/defect-rate denominators the same way a customer dispatch already didn't.

**Orders plumbing (not yet UI)**: `orders[].items[]` accepts an additive `itemType:'casting'|'assembly'` (defaults to `'casting'`, zero-migration) and `applyDispatchToOrder` takes a 5th trailing-optional `itemType` param — both land now so Phase 2/3 (assembly dispatch + assembly customer orders) are additive, but `OrdersView`'s UI stays casting-only until then.

## Preventive maintenance

`maintenance_schedules` (cap 200): `{id, machineId, title, intervalDays, lastDoneDate, notes, createdBy}` — next due = lastDoneDate + intervalDays via `maintenanceDueDate`/`maintenanceDueState` in `utils.js` (7-day due-soon lead vs 3 for orders; both delegate to the shared `dueStateForDate`). Marking done appends to `maintenance_log` (cap 1000: `{scheduleId|null, machineId, machineName, title, date, cost|null, note, doneBy}`) AND bumps the schedule's `lastDoneDate`, rolling the due date forward. Ad-hoc entries (`scheduleId:null`) log unscheduled repairs. `MaintenanceModal` (admin+supervisor topbar button with ⚠N badge). Cost is an optional number on log entries — history, not accounting. Deleting a schedule keeps its log entries.

## Analytics

`AnalyticsView` (in `src/components/dashboard/`) is a full-page view toggled from the topbar "Analytics" button (admin+supervisor) — it swaps the `main-layout` block while Topbar/ShiftBanner stay. All aggregation math lives in pure, tested `aggregate*` helpers in `utils.js` (daily output, machine/operator efficiency, defects by casting type, breakdown Pareto, maintenance cost). Data caveats: breakdown history comes from `alerts` (capped 200 → shallow); consumption for defect rates excludes `stageLabel:'Finished goods dispatch'` stock_log rows (dispatches are not production); OT ₹ KPI computes via `computeShiftPay` at current wages. Charts are CSS bars (OutputChart idiom) — no chart library.

The foundry scorecard section attributes casting defects to suppliers via `aggregateFoundryScore`: each casting type is assumed **single-sourced** (confirmed with the owner), its foundry being the supplier on its latest stock-in entry across the whole log; machining defects are excluded (our fault, not the foundry's); supplier names are normalized trim+case-insensitive (blank → "(unspecified)" bucket). StockView's Stock in supplier field has a datalist of previously used names to prevent name drift.

## Production planning

`PlanningView` (`src/components/PlanningView.jsx`, a `PageView`-shell full-page view, `'planning'` in Dashboard's `view` state) is a **read-only** "what to run next" summary over a fixed **3-day horizon** — Topbar **Insights** section, admin+supervisor (same gate as Stock/Orders/Analytics, added to the first `safeView` branch). It **stores no new data**: everything is one pure, tested helper, `buildProductionPlan({castingTypes, assemblyModels, purchasedComponents, orders, wip, machines, today, horizonDays=3})` in `utils.js`, rendered as prop-driven cards (no Firestore access of its own).

The model puts **demand vs. supply** side by side per casting type that has open-order demand: `demand` = Σ remaining-to-dispatch (`qty − dispatched`) on **open** orders; `notYetStarted = max(0, demand − finishedOnHand − wipInProcess)` (pieces needing raw + the full route); `rawShortfall = max(0, notYetStarted − rawBalance)`. A `verdict` chip follows: `covered` (finished stock ≥ demand) · `inProcess` (remainder already mid-route) · `shortRaw` (raw won't cover it — the row also joins the aggregated `toOrder` shopping list) · `rawReady`. Rough `shiftsNeeded = ceil(notYetStarted / bottleneckTarget)` where the bottleneck is the casting type's **slowest node target** (`min` of positive `nodes[].target`; null ⇒ "—"). Rows sort overdue → dueSoon → earliest due → most-to-make. Assemblies show `maxBuildable` (can-build-now) + the limiting BOM line as `bottleneck`; `lowRawNoOrders` lists idle casting types at/below their low mark; `capacity` is a **rough** machine-shift count (cnc_vmc ×2/day, others ×1/day, over the horizon) shown as a gut-check, not a schedule.

The 3-day horizon aligns with `orderDueState`'s existing `leadDays=3`, so "orders due within the window" = its `overdue`/`dueSoon` states — no new date logic. **`wipInProcess(wip, ctId)`** (`entered − finished − scrapped`, floored) was extracted from StockView's private `totalWipForCastingType` and is now the one shared definition (StockView calls it), mirroring how `finishedOnHand` was consolidated. **Assembly order-demand is 0 until the Phase-3 assembly-orders UI exists** (order lines default `itemType:'casting'`); the builder reads `itemType==='assembly'` lines but none are created yet. The view is advisory only — it never writes machine assignments.

## Inspections

The spec/1st-piece/2nd-piece measurement table (`LineInspectionModal`) serves two flows via its `mode` prop: `'setting'` (titled "Setting Approval" — operator submits first-off sizes, supervisor approves/rejects via `SettingDecisionModal`) and `'inspection'` (titled "Line Inspection" — a supervisor/admin-only button under MARK SHIFT COMPLETE records an in-shift check with no approval loop). ## Theming

Dark is the design baseline; a **light theme follows the device setting** via `@media (prefers-color-scheme: light)` — no toggle, no JS state. All palette values are CSS custom properties on `:root` (styles.css top): the light block overrides surfaces/borders/text plus **darkened accents** (accents double as text colors and must pass contrast on white), `--on-accent` (text on accent-filled buttons: #000 dark / #fff light), `--backdrop`/`--backdrop2`, and shadows. Every color tint is `color-mix(in srgb, var(--X) N%, transparent)` — **never add a hardcoded alpha-suffixed hex tint** (e.g. `#f0564f15`); it won't theme. `index.html` has dual `theme-color` metas. **Known v1 limitations**: `BADGE`/`AC`/`SHIFT_CFG` colors in `constants.js` are JS literals shared by both themes (saturated hues, legible on both; badge 8%-alpha backgrounds are just subtler on light), and the `window.open` print registers keep their own paper palette by design.

## Build / code-splitting

`vite.config.js` defines `manualChunks` (`firebase`, `react`) so vendor hashes only change when dependencies update — app deploys don't force phones to re-download ~150KB gzip of unchanged vendor code. `Dashboard` is `React.lazy` behind the login gate (App.jsx), and 16 staff-only screens are lazy inside Dashboard.jsx (top-of-file `lazyWithReload` block) — operator hot-path modals (assign, log progress, shift complete, breakdown, decisions, setting approval) deliberately stay eager. All lazy imports go through **`src/lazyWithReload.js`**, which reloads the page once on a failed chunk fetch — Netlify deploys are atomic, so a phone holding a stale `index.html` would otherwise 404 on old hashed chunks. When adding a staff-only screen, add it to the lazy block, not the eager imports. `firebase/functions` is dynamically imported inside `fb.deleteUserProfile` (its only call site).

## PWA

`public/manifest.webmanifest` + icons in `public/icons/` (generated PNGs in the app palette) + apple-touch/meta tags in `index.html` make the app installable to phone home screens. **Deliberately no service worker**: the app requires live Firestore anyway, install works without one on modern Chrome/iOS, and a service worker's stale cache would delay Netlify updates reaching shop-floor devices — do not add one without revisiting that trade-off.

## Report/print modals

`DownloadModal`, `BreakdownHistoryModal`, and `InspectionLogModal` generate printable output by building an HTML string client-side and opening it in a new window (`window.open` + `document.write` + `.print()`). This is intentional — don't refactor these into React-rendered print views without discussing it first, since it changes how the generated document is styled/printed. (`WageRegisterView`'s export is different: a CSV file via Blob download, not a print window.)
